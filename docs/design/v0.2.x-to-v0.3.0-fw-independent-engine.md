# v0.2.x → v0.3.0 — the completion engine loses its fw dependency

**STATUS: IMPLEMENTED 2026-09-11.** Ruled, parked as fundamental and
earmarked for a distant version the same morning, then un-parked and
built the same day once the impact was measured at one sitting. The
conf door (the last section) remains future work by explicit ruling.

## Background, for a reader with none

The sxcli ecosystem has two front doors. A framework binary
(sxcli.dev/fw) carries applets and services; a standalone tool
(sxcli.dev/conf) is a single command with one config struct and no
framework. Both share the same configuration engine
(sxcli.dev/conf/engine): one schema model, one parser, one tag
grammar.

Shell completion lives in sxcli.dev/completion. Its engine computes
candidates from a `Source` — a target-scoped view answering questions
like "what arguments exist", "what values may this field take" — and
its bash/zsh adapters translate candidates into shell answers. The
engine and script packages are public precisely so that anything able
to answer the Source contract can have completion.

Before this change that promise was broken in one place: the
contract's TYPES belonged to fw. `engine.Source` was a type alias of
`system.Introspector` (an fw package), and `ArgInfo` — the
description of one argument — was defined there too. The "neutral"
engine could not be consumed without depending on the fw module, and
a standalone conf tool had no completion story: conf grew the fruit
(the schema carries the `ValueHint` vocabulary — HintFile,
HintDirectory — exactly so tooling can act on it), but only fw
picked it.

## The change, as built

The contract's data types moved to the one home below every
consumer, and the interface lives with its consumer:

1. **sxcli-conf/engine owns the data.** `ArgInfo` and `PosInfo` live
   in conf's engine, beside `ValueHint`, which always lived there.
   This is domain-honest: the types describe SCHEMA, and schema is
   conf's business. The fields fw needs (`Service` — the owning
   operator name) are just fields; a standalone tool fills them
   trivially.
2. **sxcli-completion/engine owns the contract.** `Source` is the
   engine's own declared interface — nine methods returning the
   conf-engine types — and the engine imports no fw package at all.
   The nominal-type obstacle that blocked an earlier version of this
   idea (a struct in a method signature defeats structural
   satisfaction) dissolved: the structs are the same nominal types
   from conf, which both sides already depend on.
3. **sxcli-fw/system conforms.** `Introspector` stays fw's
   vocabulary; `ArgInfo`/`PosInfo` are aliases of conf's (the same
   move `ValueHint = engine.ValueHint` made long ago). fw's concrete
   Introspector satisfies completion's `Source` structurally; the
   bash/zsh adapters — fw applets, delivery vehicles — bridge
   `system.System` to the engine's `System` with a three-line
   adapter, nil views guarded. Neither module imports the other.
4. **Future, by ruling: the conf door.** `Loader` implements
   `Source` over its own schema — one applet (itself), no services,
   real arguments and positionals — plus a script-emitting knob and
   transport handling, so a standalone tool gets
   `mytool --completion-script bash` with zero fw involvement. This
   design unlocks it; nothing more.

No module cycles, no new repository; the package graph is a clean
diamond over conf.

Positional completion was built on top the same day: `Positionals()`
on the Source (and on fw's Introspector, answering from the same
catalog-only schema as `Arguments`), a slot-counting walk, and
slot-aware candidates — the shell's native file and directory
completion for hinted slots, domain values for closed ones, silence
for open ones — before and after the `--` terminator alike. The
ruled ownership: a bare word belongs to the next unfilled slot when
one exists; argument names are offered when none does, or when the
word starts with a dash. Proven end to end through real bash and
zsh.

## What it superseded

- The 2026-09-05 ruling "engine.Source stays as is" (the alias) was
  made in the fw-centric frame, before the fw-independence ruling
  existed. The alias WAS the fw dependency; the two could not both
  hold.
- Any external hand-wired `Source` implementor breaks (none known;
  the modules are v0).

## What it touched

- **sxcli-conf/engine**: gained `ArgInfo` and `PosInfo`; no behavior.
- **sxcli-completion/engine**: its own `Source`; the fw import gone;
  the slot machinery; the adapters' System bridge.
- **sxcli-fw**: system aliases, `Introspector.Positionals()`, a root
  `PosInfo` alias, the introspection pin.
- **sxcli-vet**: nothing — the aliases kept every stub truthful.
- **Tests**: engine pins for every slot branch; the bash and zsh
  smokes carry a `HintFile pos:"0"` field and assert the native file
  directive at a bare position.
